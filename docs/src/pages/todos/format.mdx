# Todo format

A TODO stores a title, body, priority, status, acceptance criteria, definition-of-done fixture and execution history. It can also carry labels, a parent, related/dependent links, PR references and a selected Captain plan revision. Resolve TODOs by short ID, full ID, title or alias.

## Create and inspect

```sh
gavel todos create --title 'Fix session cache expiry' --body @task.md --priority high --verification @verification.md
gavel todos get TODO_ID
gavel todos criteria TODO_ID
gavel todos comment TODO_ID 'Focused reproduction confirmed'
```

`--body`, `--plan` and `--verification` accept inline text or `@path`. Relative paths resolve from `--cwd`. A top-level `# Verification` or `## Verification` section in the supplied body is extracted into the stored fixture; explicit `--verification` content comes first, then extracted fixtures.

The body describes the problem, scope and acceptance criteria. The fixture contains the executable definition of done, including commands, Gavel test/lint runner blocks, tables, checklists and CEL assertions as needed. `gavel todos check TODO_ID` runs that persisted fixture and produces test results and a CEL verdict. Inspect `gavel fixtures --help` for the runner's current format.

## Durable plans

```sh
gavel todos create --title 'Repair session lookup' --body @task.md --plan @plan.md --verification @verification.md
gavel todos plan approve TODO_ID
gavel todos edit TODO_ID --plan @revised-plan.md
```

Supplying `--plan` stores an immutable Captain plan revision selected on the TODO. It awaits review by default. When the supplied plan has already been approved, creation with `--status approved` records that approval and leaves the TODO pending for execution. Plan revisions and review history remain durable; reject clears the active plan selection rather than deleting history.

## Status and relationships

`draft` and `pending` identify work before execution; `in_progress`, `review` and `ask` identify active execution, human plan review and pending questions. `verified`, `unverified`, `completed`, `failed` and `skipped` record outcomes. Lifecycle predicates determine transitions; a provider's successful response alone does not prove that the fixture passed.

`--parent TODO_ID` creates a child. Children stay out of the ordinary top-level list and counts; inspect the parent with `get` or list with `--parent`. Creation inside a TODO run inherits its TODO as parent unless `--no-parent` is supplied. Links represent related work or dependencies without changing the parent hierarchy.

## Portable Markdown

`gavel todos import` loads portable `.todos` Markdown into native PostgreSQL issues; `gavel todos export` writes portable Markdown from the database. These commands are explicit interchange operations. Editing an exported file does not update the live TODO until it is imported. Use each command's help for destination and collision controls.

Source TODO/FIXME comments enter the backlog through `gavel todos sync`. External issue publication is explicit through `gavel todos push` or creation with `--github`.
