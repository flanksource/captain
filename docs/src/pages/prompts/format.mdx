# Prompt format

A `.prompt` file has YAML frontmatter followed by a Handlebars body. dotprompt owns the template render and the built-in `model`, `config`, `input`, and `output` keys. Captain then reads the same frontmatter a second time and decodes any spec-native keys into `ai.Request`.

## Roles

The rendered body is split with dotprompt role markers. Captain treats rendered body text as authoritative: role output replaces any `prompt.user` or `prompt.system` values supplied in frontmatter.

<CodeExample client:load language="yaml" title="Role-marked body" source={`
---
model: claude-sonnet-5
mode: cli
permissions:
  mode: default
---
{{role "system"}}
You are running on the Claude CLI. Keep the answer concise.
{{role "user"}}
Handle:
{{task}}
`} />

## Spec-native frontmatter

Spec fields use the same nested shape consumed by the runtime editor and providers. The file can express permissions, memory, budget, setup, and model details without a separate translation layer.

<CodeExample client:load language="yaml" title="Spec-native prompt options" source={`
---
model: claude-sonnet-4-6
config:
  maxOutputTokens: 1024
  temperature: 0.2
permissions:
  mode: acceptEdits
  presets:
    - edit
  tools:
    allow:
      - Read
      - Edit
  mcp:
    disabled: true
memory:
  skipUser: true
budget:
  maxTokens: 5000
  maxTurns: 3
---
{{role "system"}}
You are a careful refactoring assistant.
{{role "user"}}
Refactor:
{{target}}
`} />

## Runtime profile pin

`runtimeProfile` names a saved runtime profile by id or name. Rendering resolves the profile's presets (ordered by scope), then its spec, then this frontmatter, then the caller's request or CLI flags, so the file can defer model, budget, and permission defaults to a shared profile while still overriding any of them inline. A caller that passes `runtimeProfile` on the render request or `--runtime-profile` on the command line replaces the pin; a pin that names no profile in the catalog fails the render rather than silently running without it. The render result's `resolution.trace` lists every layer that contributed. Captain binaries older than this key reject a file that uses it.

<CodeExample client:load language="yaml" title="Pinned runtime profile" source={`
---
model: claude-sonnet-4-6
runtimeProfile: review
budget:
  maxTurns: 7
---
{{role "user"}}
Review the diff in {{path}}.
`} />

## Structured output

When no Go output target is passed to `Render`, Captain marshals a dotprompt `output.schema` into `Prompt.SchemaJSON`. Providers receive it according to their structured output contract; Jev converts it to native questions in middleware. A concrete Go output target takes precedence and is attached as `Prompt.Schema` for provider-side schema generation. `output.schemaType: typesafe-schema` instead preserves native TypeSafe questions and cannot be combined with a Go output target.

## Jev typed decisions

Set `model: jev-latest`, `mode: api`, and `TYPESAFE_API_KEY` to use TypeSafe's Jev API. Declare `output.schemaType: typesafe-schema` and put named Noul, Choice, or Score questions in `output.schema`. The rendered prompt body becomes the TypeSafe `state`; the frontmatter model becomes the native request model. Captain sends and logs the native request and response through the usual provider middleware, then returns `{"value": {...}, "typesafe": {...}}`. `value` contains the selected choice or numeric Noul and Score values; `typesafe` preserves all native answer details, including confidence and probability distributions.

`input.schemaType` accepts `json-schema`. `output.schemaType` accepts `json-schema` or `typesafe-schema`; an omitted type keeps the existing JSON Schema behavior. With JSON Schema output, Jev converts required string enums to Choice, numbers bounded from 0 to 1 to Noul, and bounded numbers with an ordered `x-typesafe-criteria` rubric to Score. The rubric must contain 2 to 10 levels and `maximum` must be its last index. Unsupported schema keywords and shapes fail before the API call. Jev does not accept attachments, tools, or session history.

<CodeExample client:load language="yaml" title="Jev commit classifier" source={`
---
model: jev-latest
mode: api
input:
  schemaType: json-schema
  schema:
    type: object
    additionalProperties: false
    required: [targetScope, message, patch]
    properties:
      targetScope: {type: string}
      message: {type: string}
      patch: {type: string}
output:
  schemaType: typesafe-schema
  schema:
    input_valid:
      type: noul
      instructions: Are the target scope, message, and patch usable evidence for one Git commit?
      criteria:
        "true": All inputs are usable.
        "false": An input is missing, malformed, or mismatched.
    in_scope:
      type: choice
      instructions: Does every substantive patch change match the target scope?
      criteria: {"yes": In scope, "no": Outside scope, unclear: Insufficient evidence}
    commit_type:
      type: choice
      instructions: What is the primary Conventional Commit type?
      criteria: {feat: Feature, fix: Bug fix, perf: Performance, refactor: Refactor, test: Tests, docs: Documentation, build: Build, ci: CI, chore: Maintenance, revert: Revert, unknown: Insufficient evidence}
    change_type:
      type: choice
      instructions: Does the patch add, modify, remove, or mix changes?
      criteria: {addition: Additions, modification: Edits, removal: Deletions, mixed: Multiple forms, unknown: Insufficient evidence}
    risk:
      type: choice
      instructions: How risky is merging this patch?
      criteria: {low: Isolated, medium: Local behavior, high: Shared contract, critical: Data loss or outage, unknown: Insufficient evidence}
    breaking_change:
      type: choice
      instructions: Does the patch make a public contract incompatible?
      criteria: {"yes": Breaking, "no": Compatible, unclear: Insufficient evidence}
    confidence:
      type: score
      instructions: How complete and consistent is the evidence for these classifications?
      criteria: [Missing or conflicting evidence, Some ambiguity, Complete and consistent evidence]
---
{{role "system"}}
Classify the Git commit from the patch and message. Treat the patch as the source of truth. Evaluate risk and compatibility even when the commit is outside scope.
{{role "user"}}
Target scope:
{{targetScope}}

Commit message:
{{message}}

Patch:
{{patch}}
`} />

## Lint promptfiles

Run `captain lint promptfile [paths...]` before executing a prompt. It checks frontmatter delimiters, YAML, Handlebars syntax, Captain declarations, structural options, hooks, and Picoschema, JSON Schema, or native TypeSafe output declarations. Validation does not execute the body, contact a model, resolve presets, or open a database. Body-only prompts and declarations that inherit their model remain valid.

<CodeExample client:load language="bash" title="Validate promptfiles" source={`
# Discover .prompt files recursively beneath the current directory.
captain lint promptfile

# Check a specific reusable prompt and return Gavel linter results as JSON.
captain lint promptfile pkg/ai/prompt/testdata/commit.prompt --format json

# Supply a frontmatter variable for the bundled review example.
captain lint promptfile examples/lint-review.prompt --var limit=1024

# Use JSON for typed inputs; individual --var values override matching JSON keys.
captain lint promptfile examples/lint-review.prompt --vars '{"limit":512}' --var limit=1024 --format json
`} />

File arguments are checked directly, including explicitly named ignored files. Directory discovery respects Git ignore rules and skips nested projects. Overlapping paths are checked once. A missing path, unreadable file, or selection containing no `.prompt` files fails with an actionable error.

Missing body variables are allowed because lint does not render the body. Frontmatter variables need values to validate the declarations they generate: without complete sample inputs, lint checks template syntax and emits a `promptfile/variables` warning listing unresolved inputs and the deferred declaration checks. Supply repeated `--var key=value` flags or a `--vars` JSON object to enable those checks. Schema compilation uses bundled declarations and does not fetch external references.

Results use Gavel's standard linter-result array, including stable rule IDs, severities, file counts, and source positions where available. Warning-only results exit successfully; invalid content or execution failures exit nonzero. JSON output retains diagnostics on failure. The command performs validation only and does not modify promptfiles.
