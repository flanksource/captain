# Prompt format

A `.prompt` file has YAML frontmatter followed by a Handlebars body. dotprompt owns the template render and the built-in `model`, `config`, `input`, and `output` keys. Captain then reads the same frontmatter a second time and decodes any spec-native keys into `ai.Request`.

## Roles

The rendered body is split with dotprompt role markers. Captain treats rendered body text as authoritative: role output replaces any `prompt.user` or `prompt.system` values supplied in frontmatter.

<CodeExample client:load language="yaml" title="Role-marked body" source={`
---
model: claude-sonnet-5
mode: cli
permissions:
  mode: default
---
{{role "system"}}
You are running on the Claude CLI. Keep the answer concise.
{{role "user"}}
Handle:
{{task}}
`} />

## Spec-native frontmatter

Spec fields use the same nested shape consumed by the runtime editor and providers. The file can express permissions, memory, budget, setup, and model details without a separate translation layer.

<CodeExample client:load language="yaml" title="Spec-native prompt options" source={`
---
model: claude-sonnet-4-6
config:
  maxOutputTokens: 1024
  temperature: 0.2
permissions:
  mode: acceptEdits
  presets:
    - edit
  tools:
    Read: allow
    Edit: allow
  mcp:
    disabled: true
memory:
  skipUser: true
budget:
  maxTokens: 5000
  maxTurns: 3
---
{{role "system"}}
You are a careful refactoring assistant.
{{role "user"}}
Refactor:
{{target}}
`} />

## Inline tools

`tools` declares tools the model can call, keyed by tool name. Each tool runs its `exec` script and returns the result to the model. Inline tools are caller tools: API runtimes call them in-process and agent runtimes reach them through Captain's caller-tool MCP endpoint. A runtime that cannot expose caller tools (for example `google cli`) refuses the run before the first model call.

<CodeExample client:load language="yaml" title="A prompt that ships its own tool" source={`
---
model: agent:sonnet
tools:
  lookup_ticket:
    description: Fetch a ticket by id
    input: {id: string}
    output: {title: string, status: string}
    exec: |
      #!/usr/bin/env python3
      import json, sys
      ticket = json.load(sys.stdin)
      print(json.dumps({"title": "Ticket " + ticket["id"], "status": "open"}))
    readonly: true
    timeout: 30s
    retry: {attempts: 3, delay: 1s, exitCodes: [75]}
---
Summarise ticket {{ticket}}.
`} />

  <thead>
    <tr>
      <th>Field</th>
      <th>Behavior</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td><code>exec</code></td>
      <td>Required. The script to run. A shebang line picks the interpreter; otherwise it runs with <code>bash -c</code>, or <code>sh -c</code> when bash is missing. The tool input arrives on stdin as a JSON object.</td>
    </tr>
    <tr>
      <td><code>description</code></td>
      <td>Shown to the model.</td>
    </tr>
    <tr>
      <td><code>input</code></td>
      <td>Picoschema or JSON Schema for the arguments. Omit it to take an empty object.</td>
    </tr>
    <tr>
      <td><code>output</code></td>
      <td>Picoschema or JSON Schema. When set, stdout must be JSON that matches it, and the model gets the parsed document. Without it, the model gets stdout as text.</td>
    </tr>
    <tr>
      <td><code>readonly</code>, <code>destructive</code></td>
      <td>Safety hints. A <code>readonly</code> tool runs without approval. A <code>destructive</code> tool asks first. Declaring neither makes the tool ask, unless a policy rule allows it. The two are mutually exclusive.</td>
    </tr>
    <tr>
      <td><code>permission</code></td>
      <td><code>auto</code>, <code>ask</code>, <code>allow</code> or <code>deny</code>. Overrides the default derived from the hints. <code>toolPolicy</code> and <code>toolPreferences</code> rules still apply by tool name, as for any caller tool; <code>permissions.tools</code> does not govern caller tools.</td>
    </tr>
    <tr>
      <td><code>timeout</code></td>
      <td>Bounds each attempt. The default is <code>10m</code>. On timeout the script's whole process group is killed.</td>
    </tr>
    <tr>
      <td><code>retry</code></td>
      <td><code>attempts</code> counts every run, the first included. <code>delay</code> (default <code>1s</code>) grows by <code>backoff</code> (default <code>2</code>) up to <code>maxDelay</code> (default <code>30s</code>). A timed-out attempt is always retried. A non-zero exit is retried unless <code>exitCodes</code> is set, in which case only the listed codes are retried. Output that fails the <code>output</code> schema is never retried.</td>
    </tr>
    <tr>
      <td><code>cwd</code>, <code>dotenv</code>, <code>envVars</code>, <code>connections</code></td>
      <td>The same fields as <code>setup</code>, applied to this tool. A tool inherits the run's <code>setup</code> dotenv files, env vars and connections; its own dotenv files and env vars are added on top and win on conflict, and its own <code>connections</code> replace the run's. <code>cwd</code> defaults to the run's working directory, after any setup checkout or worktree. <code>checkout</code> is not allowed on a tool.</td>
    </tr>
  </tbody>
</table>

The script runs through the commons-db shell runner. Its environment contains only the allowlisted host variables plus the declared dotenv files, env vars and connection credentials. Values from `envVars`, `dotenv` and connections are redacted from the output and errors the model sees. A non-zero exit returns the exit code and the tail of stderr to the model as a tool error. In a sandboxed run, the script is confined by the same wrapper as `workflow.verify` commands.

The frontmatter is rendered as Handlebars before it is decoded, so `exec` can use run variables, for example `--project {{shq project}}`. A literal `{{` in a script must be written as `\{{`. Tool arguments never pass through the template: they only arrive on stdin.

A tool declared in a preset or request layer with the same name replaces the prompt's tool whole. Fields from the two layers are never mixed. `captain lint promptfile` compiles each tool's schemas. It warns when a `destructive` tool retries, because a failed attempt may already have taken effect.

## Runtime preset selection

`presets` selects reusable runtime spec layers. Captain combines the selected presets, rendered frontmatter, and caller request, sorting by explicit `order`, then scope, then selection order. Ordinary presets supply defaults beneath the prompt; a higher `order` can enforce fields afterward. Saved configuration fills remaining gaps. Missing or ambiguous references fail rendering. The render result's `resolution.trace` and `resolution.provenance` explain the effective fields. See [Runtime overlay](/prompts/runtime/#precedence).

`runtimeProfile` and `--runtime-profile` are deprecated and ignored with a warning. Replace them with `presets` and `--preset`.

<CodeExample client:load language="yaml" title="Reusable runtime presets" source={`
---
model: claude-sonnet-4-6
presets: [Plan]
budget:
  maxTurns: 7
---
{{role "user"}}
Review the diff in {{path}}.
`} />

## Structured output

When no Go output target is passed to `Render`, Captain marshals a dotprompt `output.schema` into `Prompt.SchemaJSON`. Providers receive it according to their structured output contract; Jev converts it to native questions in middleware. A concrete Go output target takes precedence and is attached as `Prompt.Schema` for provider-side schema generation. `output.schemaType: typesafe-schema` instead preserves native TypeSafe questions and cannot be combined with a Go output target.

## Jev typed decisions

Set `model: jev-latest`, `mode: api`, and `TYPESAFE_API_KEY` to use TypeSafe's Jev API. Declare `output.schemaType: typesafe-schema` and put named Noul, Choice, or Score questions in `output.schema`. The rendered prompt body becomes the TypeSafe `state`; the frontmatter model becomes the native request model. Captain sends and logs the native request and response through the usual provider middleware, then returns `{"value": {...}, "typesafe": {...}}`. `value` contains the selected choice or numeric Noul and Score values; `typesafe` preserves all native answer details, including confidence and probability distributions.

`input.schemaType` accepts `json-schema`. `output.schemaType` accepts `json-schema` or `typesafe-schema`; an omitted type keeps the existing JSON Schema behavior. With JSON Schema output, Jev converts required string enums to Choice, numbers bounded from 0 to 1 to Noul, and bounded numbers with an ordered `x-typesafe-criteria` rubric to Score. The rubric must contain 2 to 10 levels and `maximum` must be its last index. Unsupported schema keywords and shapes fail before the API call. Jev does not accept attachments, tools, or session history.

<CodeExample client:load language="yaml" title="Jev commit classifier" source={`
---
model: jev-latest
mode: api
input:
  schemaType: json-schema
  schema:
    type: object
    additionalProperties: false
    required: [targetScope, message, patch]
    properties:
      targetScope: {type: string}
      message: {type: string}
      patch: {type: string}
output:
  schemaType: typesafe-schema
  schema:
    input_valid:
      type: noul
      instructions: Are the target scope, message, and patch usable evidence for one Git commit?
      criteria:
        "true": All inputs are usable.
        "false": An input is missing, malformed, or mismatched.
    in_scope:
      type: choice
      instructions: Does every substantive patch change match the target scope?
      criteria: {"yes": In scope, "no": Outside scope, unclear: Insufficient evidence}
    commit_type:
      type: choice
      instructions: What is the primary Conventional Commit type?
      criteria: {feat: Feature, fix: Bug fix, perf: Performance, refactor: Refactor, test: Tests, docs: Documentation, build: Build, ci: CI, chore: Maintenance, revert: Revert, unknown: Insufficient evidence}
    change_type:
      type: choice
      instructions: Does the patch add, modify, remove, or mix changes?
      criteria: {addition: Additions, modification: Edits, removal: Deletions, mixed: Multiple forms, unknown: Insufficient evidence}
    risk:
      type: choice
      instructions: How risky is merging this patch?
      criteria: {low: Isolated, medium: Local behavior, high: Shared contract, critical: Data loss or outage, unknown: Insufficient evidence}
    breaking_change:
      type: choice
      instructions: Does the patch make a public contract incompatible?
      criteria: {"yes": Breaking, "no": Compatible, unclear: Insufficient evidence}
    confidence:
      type: score
      instructions: How complete and consistent is the evidence for these classifications?
      criteria: [Missing or conflicting evidence, Some ambiguity, Complete and consistent evidence]
---
{{role "system"}}
Classify the Git commit from the patch and message. Treat the patch as the source of truth. Evaluate risk and compatibility even when the commit is outside scope.
{{role "user"}}
Target scope:
{{targetScope}}

Commit message:
{{message}}

Patch:
{{patch}}
`} />

## Lint promptfiles

Run `captain lint promptfile [paths...]` before executing a prompt. It checks frontmatter delimiters, YAML, Handlebars syntax, Captain declarations, structural options, hooks, and Picoschema, JSON Schema, or native TypeSafe output declarations. Validation does not execute the body, contact a model, resolve presets, or open a database. Body-only prompts and declarations that inherit their model remain valid.

<CodeExample client:load language="bash" title="Validate promptfiles" source={`
# Discover .prompt files recursively beneath the current directory.
captain lint promptfile

# Check a specific reusable prompt and return Gavel linter results as JSON.
captain lint promptfile pkg/ai/prompt/testdata/commit.prompt --format json

# Supply a frontmatter variable for the bundled review example.
captain lint promptfile examples/lint-review.prompt --var limit=1024

# Use JSON for typed inputs; individual --var values override matching JSON keys.
captain lint promptfile examples/lint-review.prompt --vars '{"limit":512}' --var limit=1024 --format json
`} />

File arguments are checked directly, including explicitly named ignored files. Directory discovery respects Git ignore rules and skips nested projects. Overlapping paths are checked once. A missing path, unreadable file, or selection containing no `.prompt` files fails with an actionable error.

Missing body variables are allowed because lint does not render the body. Frontmatter variables need values to validate the declarations they generate: without complete sample inputs, lint checks template syntax and emits a `promptfile/variables` warning listing unresolved inputs and the deferred declaration checks. Supply repeated `--var key=value` flags or a `--vars` JSON object to enable those checks. Schema compilation uses bundled declarations and does not fetch external references.

Results use Gavel's standard linter-result array, including stable rule IDs, severities, file counts, and source positions where available. Warning-only results exit successfully; invalid content or execution failures exit nonzero. JSON output retains diagnostics on failure. The command performs validation only and does not modify promptfiles.

## Review documents with Gavel

`gavel lint prompt` runs a prompt with the `lint` preset, which replaces the prompt's output schema with Gavel's violation contract, so any prompt that asks for located findings works as a linter. Captain ships five built-in document review prompts, resolved by name from any directory. They run as read-only agents: they read the listed files themselves, search the working tree to check concrete references, and report each finding with its file, line, quoted text, severity and a stable `family/name` rule id. Errors fail the lint; warnings and info do not.

<table>
  <thead>
    <tr><th>Prompt</th><th>Reader</th><th>Rule families</th></tr>
  </thead>
  <tbody>
    <tr><td><code>spec-internal-high</code></td><td>Team deciding what to build: PRDs, RFCs, architecture overviews, plans</td><td><code>req/</code> <code>doc/</code> <code>hl/</code> <code>int/</code></td></tr>
    <tr><td><code>spec-internal-low</code></td><td>Implementers: detailed, schema and algorithm designs</td><td><code>req/</code> <code>doc/</code> <code>ll/</code> <code>int/</code></td></tr>
    <tr><td><code>spec-public-high</code></td><td>Customers evaluating: product specs, solution overviews, whitepapers</td><td><code>req/</code> <code>doc/</code> <code>hl/</code> <code>pub/</code></td></tr>
    <tr><td><code>spec-public-low</code></td><td>External integrators: API references, protocol and format specs</td><td><code>req/</code> <code>doc/</code> <code>ll/</code> <code>pub/</code></td></tr>
    <tr><td><code>proposal-review</code></td><td>Evaluators: RFP responses, proposals, statements of work</td><td><code>req/</code> <code>doc/</code> <code>prop/</code></td></tr>
  </tbody>
</table>

`req/` checks requirement quality (verifiable, unambiguous, singular, with units, consistent). `doc/` catches defects common in generated documents: unsourced numbers, cross-section inconsistencies, placeholders, boilerplate, and planned behavior described as existing. `hl/` and `ll/` hold each level to its job, so a PRD is not asked for field types and an API reference is not asked for market rationale. `int/` verifies references against the repository; `pub/` catches internal leaks, undefined terms and missing versioning. `prop/` traces every mandatory RFP requirement to the response when `rfp` is supplied.

Each review prompt declares `permissions: {access: read-only}` rather than a tool list. The same file therefore runs read-only on claude, where it compiles to Edit, Write, Bash and sub-agent denies, and on codex, where it compiles to a read-only sandbox that never asks. Web tools stay available on both. `captain permissions explain proposal-review --model agent:sonnet --model agent:gpt-6.1-sol` shows both postures; see [Portable access](/prompts/runtime/#portable-access).

To customize a built-in prompt, copy it from `pkg/ai/prompt/builtin/` into `~/.config/captain/prompts/`, or into a repository's `.captain/prompts/`, under the same name. The local copy shadows the built-in.

<CodeExample client:load language="bash" title="Review documents" source={`
# Validate the prompt declarations without calling a model.
captain lint promptfile pkg/ai/prompt/builtin/spec-internal-high.prompt --var files=docs/prd.md

# Show the rendered request, including the lint schema and read-only permissions.
gavel lint prompt spec-internal-high -V files=docs/prd.md --dry-run

# Review a design against the high-level spec it implements.
gavel lint prompt spec-internal-low -V files=docs/design.md -V parent=docs/prd.md

# Review several public documents with an extra focus, grouped by rule.
gavel lint prompt spec-public-low -V files="docs/api.md docs/errors.md" -V focus="pagination" --summary

# Trace an RFP response against the RFP.
gavel lint prompt proposal-review -V files=bid/response.md -V rfp=bid/rfp.md
`} />
