# Embedding a run

`pkg/promptrun.Run` executes one resolved prompt spec through captain's generate→verify loop: attachment checks, provider construction, tool-policy enforcement, the workflow's commit and verify hooks, the caller's own hooks, the setup plugin, and finally `agent.Runner`. It is the seam `captain prompt run` and an embedding host (gavel's todo lifecycle) share, so the two never assemble the same pieces by hand and drift.

The caller renders and resolves the spec, prepares attachments against a store, and consumes events through `OnEvent`. Captain owns persistence when `Input.Record` is set; the host links its own rows through `Recording.Link` rather than writing Captain's tables.

## `Input`

<CodeExample client:load language="go" title="pkg/promptrun.Input (main fields)" source={`
type Input struct {
    Resolved          api.ResolvedSpec  // final spec, raw trace, provenance and warnings; attachments prepared
    RuntimePresets    *runtimeprofiles.PresetResolution // records selected presets
    Record            *promptrun.Recording // nil leaves the run unrecorded
    Approvals         *promptrun.ApprovalOptions // durable per-run approval broker
    Config            ai.Config         // builds the provider when Provider is nil: model, credentials, sandbox, cache, OnApproval
    Provider          ai.Provider       // set to use as-is; taken to own the workspace (a remote sandbox, or a test double)
    Hooks             []any             // the caller's own agent hooks
    CallerOwnsCommits bool              // hands committing to Hooks; Run builds no commit hook of its own
    Verify            verify.Options    // Provider/RunSpec are filled in when nil; Progress receives in-flight snapshots
    OnEvent           func(iter int, ev ai.Event)
    Timeout           time.Duration     // bounds the run when spec.budget.timeout is empty; no compiled-in default
    MaxIterations     int               // overrides workflow.verify.maxIterations; 0 means the workflow decides
    Scope             agent.Scope       // overrides workflow.verify.scope; empty means the workflow decides
    NoStream          bool              // forces buffered execution even on a streaming provider
    Repo              string            // root the run's changed files are recorded relative to; empty means the request's cwd
    ContextSources    []promptcontext.Source // optional initial-prompt enrichment hooks
}
`} />

- **`Provider`** — when set, `Run` takes it as owning the workspace: a remote-executing sandbox that materialises the checkout on its own side, or a test double. `Run` adds no setup hook in that case. When nil, `Run` constructs the provider from `Config` and prepares `Request.Setup` through the setup plugin, in-process.
- **`CallerOwnsCommits`** — for a host whose own commit pipeline runs the commit (gavel's pre-commit gates and trailers): `Run` builds no commit hook from `Workflow.Commits`, and leaves the declaration on the request so the recorded spec still says what the run commits, and validation of that declaration still runs. `Hooks` must be non-empty when this is set — nothing would commit otherwise, and `Hooks()` refuses the run rather than silently doing nothing.

## Timeout rule

Call `promptrun.Preflight(input)` before dispatch to check the same resolved request that `Run` will admit. It validates declarations, attachments, deadlines, model selection, runtime policies, judge prompt files, verifier registration and commit ownership without constructing a provider or running setup. Log its returned warnings separately from fatal errors. `Run` applies configured prompt-context hooks before admission and repeats its admission checks before execution.

<CodeExample client:load language="text" title="runTimeout precedence" source={`
1. spec.budget.timeout  — wins when declared: it is what the run's author chose
2. Input.Timeout        — the caller's default, used only when the spec declares none
3. (no third fallback)  — error: "no timeout: declare budget.timeout on the spec or set Input.Timeout"
`} />

There is deliberately no compiled-in ceiling. An earlier fallback capped a run that had declared nothing, so a job that legitimately needed an hour died at a couple of minutes with a deadline nobody had chosen and nothing naming it.

## Verify-only runs

A spec with an empty `prompt.user` but a declared `workflow.verify` is **verify-only**: generation is skipped and the run scores the state that already exists (`api.Spec.IsVerifyOnly`). `Run` classifies every request exactly once, through `Request.ValidateRunnable`, so the caller building the provider and the runner deciding whether to call a model can never disagree about what kind of run this is.

An attachment-only request with no generation input and no declared verifier is not verify-only. `ValidateRunnable` rejects an empty run rather than reporting a pass without generation or verification; conversation and resume payloads must satisfy their own runnable-input validation.

A verify-only run of only `commands` and a `fixture` needs no model and builds no provider — it must work without credentials to hand. A verify-only run that also declares `prompts` (LLM judges) still builds one, because the judge needs it.

`OnEvent` taps the live event stream — the model's events and the hooks' — with the runner's own signature: `iter` names the turn an event belongs to, which a renderer needs and a single-turn caller ignores.

## `Result`, final report and merging

<CodeExample client:load language="go" title="pkg/promptrun.Result" source={`
type Result struct {
    PromptRunID     uuid.UUID             // recorded row, or nil UUID when Record was unset
    Response        *ai.Response          // final text, structured data, terminal outcome, workspace
    Verdicts        []agent.VerifyResult  // every verify verdict, in the order it was reached
    Report          *api.VerifyReport     // the last round's rolled-up report
    Passed          bool                  // Passed(Verdicts): the final round's verdict, or true when nothing was declared
    Loop            *ai.LoopResult        // nil for a verify-only run
    StructuredData  any
    TerminalOutcome *api.TerminalOutcome
    SessionID       string
    Model           string
    Usage           api.Usage
    CostUSD         float64
    Duration        time.Duration
}
`} />

`Passed`, `FailureReason`, and `FinalReport` are exported functions over `[]agent.VerifyResult`, not methods that could disagree with what the runner itself decided:

- **`Passed(verdicts)`** is `agent.VerifyPassed(verdicts)` — the rule the runner sets `HookContext.Verified` from — so a caller reading `Result.Passed` and a `Post` hook reading its context never disagree about whether the run verified.
- **`FailureReason(verdicts)`** is the last failing verdict's reason, empty when the run passed.
- **`FinalReport(verdicts)`** is the run's verdict as one report: a round runs every verifier the workflow declares, so it produces one report per verifier. Taking only the last of them used to throw the rest away — a round of `commands` + `fixture` came back as the fixture's tree alone. A round of one report is that report unwrapped; a round of several is `api.MergeReports`, which nests each report under its own group node (its own `summary` carried on the node, not recomputed, so an elided suite still contributes its whole tally) and passes only when every report in the round passed.

## Serving prompts and prompt runs over HTTP

For recorded execution, `Admit` creates the placement session, prompt run and host link in one transaction; a failed link dispatches nothing. `Run` records iterations, notices, verification progress and terminal state. `Settle` records the outcome of a parked run completed outside `Run`; `Fail` and `Cancel` settle with a reason. See [pkg/promptrun](https://github.com/flanksource/captain/tree/main/pkg/promptrun) for recording inputs and lifecycle details.

A host that serves captain's prompt surface instead of calling `promptrun.Run` itself wires four pieces from `pkg/cli`:

<CodeExample client:load language="go" title="Embedding the prompt HTTP surface" source={`
cli.RegisterPromptEntity()                // before clicky builds the CLI / rpc executor
stop := cli.StartSessionHost(ctx)         // prunes finished runs, stops live chats on exit
defer stop()

mux.Handle("/api/captain/prompt/runs/", http.StripPrefix("/api/captain/prompt/runs", cli.PromptRunHandler()))
mux.Handle("/api/captain/sessions/", http.StripPrefix("/api/captain/sessions", cli.SessionHandler()))

// Embedded prompts are a read-only source that resolves by bare name.
handler := cli.PromptSourcesMiddleware(root, cli.PromptSources{
    FS: []cli.PromptFS{{Label: "gavel", FS: prompts}},
})
`} />

- **Start**: `POST <executor prefix>/prompt/run?id=<prompt id or bare name>` with a `PromptRenderRequest` body (`{"variables": {...}, "presets": [...], "spec": {...}}`) answers a `PromptRunResult` (`{"runId", "status": "running", "model", "provider", "mode", ...}`).
- **Follow**: `GET /api/captain/prompt/runs/{runId}/stream` is SSE: a `run` frame whose `sessionId` is followable at `/api/captain/sessions/{id}`, then `entry`, `state` and `verify` frames, ending in `done` or `error` carrying a `PromptRunSummary`. `GET /api/captain/prompt/runs/{runId}` is the same state as one JSON snapshot.
- **Stop**: `POST /api/captain/prompt/runs/{runId}/stop`.
